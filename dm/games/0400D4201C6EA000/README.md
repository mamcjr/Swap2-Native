# Mario Tennis Fever (`0400D4201C6EA000`)

A Switch 2 game: update v327680 (1.1.1) over the base game, SDK 20.5.17 built for the Switch 2 (`Ounce`), NVN2. Camelot's engine (`nxe`) on NintendoWare (G3d, Ui2d, Vfx, Atk), with Enlighten, Pia and NPLN. Modules `main` and `sdk`, plus one NRO that `main` decodes at run time. **Plays on the Mac** (M4 Pro): the title movie, the practice, the main menu, Adventure's opening story, and Free Play singles on Stadium Court (Grass) with real rallies, at 60 fps. No IPA has been built. **Status on Android: playable, in bring-up (2026-11-12).** On the Odin 3 (Adreno 830) a whole tournament ran at about 60 fps on Mainline Turnip v32; Qualcomm's driver hangs (see Open). Packs come from the desktop packer only. The profile and its shader tables come from nxnative (`b6dbb851`), where the game plays on the Mac. **In Swap2-Native: in bring-up** ([Swap2-Native](#swap2-native)); the profile and the facts below are upstream Banana Native (eden/v0.3.42, `14a31c5d`)'s, for the same build.

## What it needs

| Setting | Where | Why |
|---|---|---|
| `mem_alias 0x500000000`, `mem_reserve 0x650000000` | [`game.tsv`](game.tsv) | `nninitStartup` asks `StandardAllocator` for 16 GB of address space, and this SDK keeps its 1 GB node area (no node-area cut matches it): with a 16 GB alias region `CentralHeap::Init` aborted (`sdk+0x13f698`) |
| `mem_stack 0x10000000`, `app_pool 0x240000000` | `game.tsv` | Splatoon Raiders' values, the Switch 2's 9 GB, not measured here |
| `sys_resource 0x2000000` | `game.tsv` | the NPDM declares 32 MB, so virtual address memory is on |
| `pad_layout full` | `game.tsv` | the game asks for most of the controller |

Render conditions, which the host evaluates for every game ([Conditional rendering evaluated at replay](../../../docs/reference/rendering.md#conditional-rendering-evaluated-at-replay); until 2026-11-12 the profile key `render_cond`): as the console does. Off, a rally looks the same and takes about 0.7 of 9.5 ms more GPU (one run each, with another job on the Mac) and logs a red line.

The NRO and the archive need no key: the NSP script captures one and `shader_split.py` reads the other (below).

## Files

- A dump folder (`base/`, `updates/327680/`): `build_ipa_from_nsp.py <folder> --platform mac` packs it with no keys. The display version `v327680` is a placeholder, as a dump has no control data.
- `main` has about 600 KB of code. It is a boot stub (`nxboot`): six threads unscramble and unpack the game's code, a 24.7 MB NRO, out of its data segment, and it loads that with `nn::ro` (A game that decodes its code at run time). The NSP script captures it from a boot in about 2 s. Its SHA-256 is the one the RomFS's NRR registers (NRR version 1). The stub obfuscates its strings and streams, but runs as it is: no game code is changed for this.
- The RomFS is `42` (7.6 GB, magic `CRA.`) and the NRR. `42` holds 8,671 files, listed only in the NRO: 5,474 sound, 164 WebM movies, the rest NARC containers of FRES, FSHA, BNTX, VFXB, SARC (One scrambled archive indexed by the NRO). `dm/gfx/tools/cra.py <42> <NRO> <folder>` writes them out.
- Movies: VP9 WebM with Vorbis, up to 2560x1440 at 60 fps; the title movie is 368 MB. The game reads them itself from the archive and feeds the SDK's extractor (`AppendMediaSourceData`).

## Shaders

35,045 in [`shader_map.tsv`](shader_map.tsv): 26,096 from models (one FSHA each), 5,331 from `ssg_system`, 3,316 from effects, 138 from `shader/`, 124 from layouts, 40 in the NRO's data. All translate. A full build takes about an hour on an M4 Pro with another job running (not timed from an empty cache in one go). [`pso_manifest.tsv`](pso_manifest.tsv) (1,351 lines) is one Mac session: boot, the movie, the menus, a match.

One does not load (current): `3032440e5027bbe5`, `shader/audience/audience_compute`, reads `array<texture2d<float>, 32> cp_t2d_cb0_0`, the compute texture handles of NVN2's per-shader `c[0]` indexed by its workgroup ID. `dmsh_reflect.py` `c2_array` only knows c2; fixing it is a chain change. The dispatch is skipped, a red line says so, and the crowd still draws; what the shader adds has not been seen.

## Rendering

- The scene renders at 2048x1152 into a 2560x1440 window texture, and the game crops the window to that (`nvnWindowSetCrop`). `DM_NVN_SHOT` takes the whole texture, so shots have a black band on the right and bottom; the window does not.
- Deferred: albedo and normals, then lighting into R11G11B10F, the atmosphere over it, bloom, an ACES tonemap. The atmosphere's table is a 3D texture of 8x8x64, filled once per stage with one draw per plane through a geometry shader that picks the layer (A passthrough geometry shader that writes the layer: the blue wash).
- Frame time in a rally, in a window of 300 frames, with another session's regression on the Mac: p50 16.6–17.2 ms, p95 about 18 ms, GPU p50 about 9 ms, p95 about 11 ms. A few single frames take 90–140 ms, not traced (open); a run after the prewarm list has not been compared.

### Resolution

- **The scenes' size (current, 2026-11-14).** One function of `nro0` (1.1.1: `nro0+0x125e980`) takes a base by the operation mode, console 2560x1440 and handheld 1920x1080, caps it by `vi::QueryDisplayBufferMaxResolution` in one performance mode, then applies the Switch 2 graphics scale (`oe::GetCurrentGraphicsScale`, stored at `nro0+0x3ecb31c` and read only there): scale 1 takes 4/5 of the base, scale 2 2/3, any other value keeps it. So the game draws console 2048x1152 at its start (scale 1), handheld 1920x1080 at scale 0 and 1280x720 at scale 2, and nothing smaller.
- **Game settings › Resolution** ([`game.tsv`](game.tsv) `graphics_scale` rows; `android_window original` keeps the game's own start as the default): Original and Phone 1440p are console scale 1 (2048x1152), Phone 1080p is handheld scale 0, Phone 720p is handheld scale 2. **Phone 540p** is handheld scale 2 plus `DM_GRAPHICS_SIZE=960x540` (the launcher passes it for a row whose scale and mode a larger row has, `Profile.gateSize`): an observation gate where the function's paths join (`nro0+0x125eb98`, [`patches.py`](https://git.eden-emu.dev/moceure/BananaNative/src/tag/eden/v0.3.42/dm/games/0400D4201C6EA000/patches.py), `dm/host/android/mtf_size.c`) writes that size into the scene's size record and w9, never above the game's own pick. Phone 480p takes 540p. The in-game panel changes it live: the scale, mode and size in one call, one message 300 (`nxhost_graphics_set`); on the Odin 3 (system driver, 2026-11-14) 540p → 720p → 1080p → 540p → 1080p each resized the scenes (`WindowCrop` 960x540, 1280x720, 1920x1080, ...) with no new `[RED]` line, before that change 540p → 1080p passed through 720p. This is a cut of the game's own code at a fixed address, keyed by `nro0`'s build ID; another build draws its own sizes ([Open](#open)).
- **Why it matters: the game counts frames.** It steps once a presented frame at interval 1, with no fixed steps (`fps_steps`) or sead rate (`fps_decouple`), so Game settings shows no Frame rate cap or Hold 60 fps. A frame over 16.7 ms is shown at the next vsync: 30 fps and half speed, as a console would slow (Forgejo #302, #307). [Full game speed at low frame rates](#full-game-speed-at-low-frame-rates) skips late frames' presents through the game's own draw flag (phone check open); a smaller scene is the other lever.
- Measured on the Odin 3 (Adreno 830, the Android test app, Mainline Turnip v32, the tutorial court, 2026-11-14): the GPU clock the governor held for 60 fps was 660–734 MHz at 2048x1152, 607–660 at 1920x1080 and 525 at 1280x720 (of 1,100); GPU time per frame stayed about 12.7 ms because the clock follows the work. The largest step is 24 full-scene quads (3.5 ms at 2048x1152, 1.9 ms at 1280x720); the 1024x1024 shadow pass (1.5–2.1 ms) does not scale.

## Full game speed at low frame rates

Current (2026-11-16, static research and unit tests; no phone run yet). The general part is in [A game that counts frames plays at half speed at 30 fps](https://git.eden-emu.dev/moceure/BananaNative/src/tag/eden/v0.3.42/docs/reference/frame-rate.md#a-game-that-counts-frames-plays-at-half-speed-at-30-fps).

- **How the engine steps (nro0 1.1.1).** Game logic is sequential code that calls WaitFrame(n) (`nro0+0x11fa2e0`; 394 call sites, 379 with n = 1). Each iteration bumps two global frame counters (`0x3ea0018`), steps the game's xorshift RNG, runs the frame function `0x11f82a0`, then `0x11f75b0` (input, focus, the next command buffer). The load and boot loops call the frame function directly (26 callers in all, each followed by `0x11f75b0`). The present interval is `min(framework+0x5cb8, 5)` (0x11f9850 / 0x11f986c). That counter goes up on every call (0x11f974c) and is cleared after a present (0x11f98c8). There is no sead, no delta time the world reads, and no step count.
- **The draw flag, `nro0+0x17999bc`** (GOT `0x1760c20`, initial 1). Readers in the frame function:
  - 0x11f8638 and 0x11f8720: the job lists' dispatch, `O->vtable+8` on `[base+0x3818]`, `base+0x90` and `[base+0x3810]`, with O = `[[0x44fd220]+0x78]`. Their wait, `O->vtable+0x20` (0x11f8748..0x11f878c), and the lists' re-arm run on every frame.
  - 0x11f9330: the submit block. It sets framework+0x5008 bit 0, submits the pending buffer at `[0x17611d0]`, then `0x25440` (`nvnQueueSubmitCommands` + `FenceSync`).
  - 0x11f975c: the present block. It holds the presented-frame count `0x17999ac`, the sync wait, the present helper `0x254f4` with the interval, the post-present queues `0x11a2504`, `0x11d0f14` and `0x11f9a40`, and the counter's reset.
  - 0x11f98f4: the shown frames' buffer index (`+0xac` of `[[0x3ec1080]+0x160]`, flipped on each shown frame).

  All 35 stores of the game write 1, and `0x11f75b0` writes 1 after every frame (0x11f7664, on its only path that returns). The frame function's only exit before the first gate is an abort (0x11f83e0). The job table is `nro0+0x3ea5160` (GOT `0x1760c30`): count u32 at +0xe000, (function, object) at +0x1050 / +0x1058 + 0x68·i, and a vector of 0x30-byte callables at +0xe010. It is filled during the step, sorted at the frame's start (`0x11a8580`, from 0x11f8578, before the first gate), and cleared after the submit block (0x11f9518, also on a skipped frame).
- **The skip** ([`patches.py`](https://git.eden-emu.dev/moceure/BananaNative/src/tag/eden/v0.3.42/dm/games/0400D4201C6EA000/patches.py) OBS rows, kind `OBS_MTF_SKIP`; [`game.tsv`](game.tsv) `fps_decouple skip`; `dm/host/android/mtf_speed.c`). The first gate, at 0x11f8624 (`ldr x21,[x21,#0xc20]`, `f94612b5`), decides. The second, at 0x11f932c (`ldr x8,[x8,#0xc20]`, `f9461108`), writes 0 for a skipped frame. So a skipped frame still dispatches and waits for its jobs, and records its layers and its main command buffer. What it leaves out is the submit, which is the host's translation and the GPU work, and the present. The frame after it does not wait at 0x11f8680, because bit 0 of framework+0x5008 stays clear. The skipped frame itself waits there for the last submitted frame. Both words are position independent, and the rewrite of 1.1.1 places them (`nro0.obs.tsv`: gates 38 and 294). Game settings and the in-game panel show Full game speed at low frame rates (on by default). The Frame rate cap row stays the game's own, and presentation stays the game's interval (`present_interval` default `game`). Do not set `DM_PRESENT_INTERVAL=display` for this game: the host turns the skip off there.
- **Phone checks, in order** (the test app, the system driver and Turnip V39 each, about 20 s of a rally; open):
  1. P1, the dormant path: `DM_MTF_SKIP_TEST=60` (one frame in 60 not submitted or presented). Expect no hang, no new `[RED]` line, and a correct picture on the next frame. Then the same with `DM_MTF_SKIP_EARLY=1`: whether the jobs' wait returns for lists that were not dispatched. If it does, the early form also saves the jobs' CPU work.
  2. P2, the signature: `DM_MTF_SKIP_LOG=1` in a rally. The job signature should be steady and change only at serves, cut-ins and scene changes. If it changes every frame, nothing is ever skipped (the 300-frame line shows 0 skipped).
  3. P3, the speed: at a load that holds 30-45 fps (Phone 1440p, or the system driver), the `mtf skip:` lines should give game time ≈ 1.0 of real time, and a stopwatch on a serve or a rally against a 60 fps run should agree. Check particles and animations too: if the NW Vfx or skeletal calculation runs in the jobs, they are cosmetic only, because the jobs still run here.
  4. P4, the cost: compare the line's "ms after a shown frame" and "after a skipped one". When a skipped frame plus a step take more than 16.7 ms, the step itself is the bottleneck and the skip gives nothing.
  5. Off: Full game speed off in the in-game panel, and `mtf skip: off`, should play as before.
- **Doubts.**
  - Whether the dispatch's wait returns for lists that were not dispatched (O's vtable was not resolved statically) is why the early form is not the default.
  - A skipped frame's GPU timestamps (the ring of 8 at framework+0x5cb0, probably the `0x24b00` call at 0x11f91a4 into the main command buffer, whatever the flag) are never written, and `0x11a4360` reads them 8 frames later as a frame-time monitor.
  - A one-shot pass recorded straight into the main command buffer by step code, not as a job, would not change the signature and could be lost.
  - `0x11f9e80`, a second frame-like path with its own submit, has no direct callers and is not gated.

### Aspect ratio

Current (2026-11-16; experimental, unit-tested, not run on a phone yet). Game settings › Aspect ratio lists 21:9, 4:3, 10:9 and 1:1 ([`game.tsv`](game.tsv) `aspect` rows; Screen shape comes with them) and sets `DM_VK_PICTURE_ASPECT`: the present fits the game's 16:9 frame into that shape. Eight observation gates on `nro0` 1.1.1 (`250a510a934129cb38e930c9a29082b6`; [`patches.py`](https://git.eden-emu.dev/moceure/BananaNative/src/tag/eden/v0.3.42/dm/games/0400D4201C6EA000/patches.py) `OBS`, kind `OBS_MTF_WIDE` 38, host `dm/host/android/mtf_wide.c`, shared parts in `wide_shape.h`) make the gameplay camera and the layouts follow it; 16:9 and any other `nro0` build run no callback. `main` is a boot stub, so the build check is on the NRO (`ws_aspect_nro`). The new gates change the rewritten `nro0`, so players re-Prepare once.

- **The camera's aspect (kind 0).** `nro0+0x11a2660` is the display layout setter (x0 the layout, w1 the mode, x2 the views' sizes). It keeps the mode at layout `+0x20`, the view count at `+0x24` (mode 0: one view; modes 1-3: two to four; 4 and up: two; `nro0+0x11a27f4`), view 0's size at `+0x2c`, and ends by writing each view's width over height into the camera array (GOT slot `nro0+0x175ecd8`, stride 0x330): `nro0+0x11a2fc8` `str s0,[x20,#0x40]` is camera 0's aspect. It runs at every layout apply, the scene size function's resize (`nro0+0x125ec28`) among them; no other store to that field goes through the array's GOT slot (a scan of `nro0`'s code). The gate, before that store: with one view and an aspect within 0.01 of 16:9 the aspect becomes the picture's. Two or more views keep theirs: the viewport function `nro0+0x11da0c0` builds each view of a multi-view layout as a 16:9 box (`nro0+0x11da5d0`) inside the 16:9 frame. Log: `mtf wide: camera aspect 1.7778 -> 2.3333 (one view, Hor+)`.
- **The vertical field of view (kind 1, narrower pictures: Vert+).** Camera 0's fovy (`+0x4c`, radians, the vertical angle: the frustum's half height is tan(fovy / 2) × near, its half width that × aspect) is written by the game every frame: the camera directors `nro0+0x969174` and its twin `nro0+0x98e940` copy their own fovy and eye into camera 0 (`nro0+0x969e40`, `nro0+0x990068`) and call its update, `nro0+0x990cd0` reads camera 0's fovy back as a blend's start, and the debug camera `nro0+0x933568` adds to it. A scaled value in memory would be scaled again or fed back, so the gates change only the register, after each load of fovy in the projection builders: `nro0+0x932378` (the table path; s1 from `ldp s5,s1,[x19,#0x48]` at `nro0+0x931ef0`, which nothing in between writes and nothing branches into), `nro0+0x93252c` (the culling frustum) and `nro0+0x932700` (the second frustum at `+0x2f8`) in the updater `nro0+0x931868`, and `nro0+0x9334ac` in its refresh `nro0+0x933358`; these are the only loads of `+0x4c` in the two. Only camera 0 holding the aspect kind 0 wrote is changed: the half angle's tangent grows by (16/9) / aspect (`ws_vertplus_half`, under 172 degrees). Wider pictures keep the fovy (Hor+). Log: `mtf wide: camera fovy 0.6000 -> 0.7824 rad (Vert+)` (4:3).
- **The layouts (kinds 2-4).** `nro0+0x11d54a0` sets a layout's draw info up: an ortho projection from the layout rect (1920x1080 units), or a perspective one for a layout with a field of view, built at `sp+0x80` (row by row, the x row first) and copied into the draw info's `+0x10` by `nro0+0x665fc` (a plain 64-byte copy) at `nro0+0x11d6620`. Kind 2, the instruction before that `bl` (`nro0+0x11d661c`; straight-line code from the merge `nro0+0x11d649c`, x1 the matrix, not written in between), scales a 16:9 matrix's x row (wider) or y row (narrower), so the layout sits in the middle 16:9. Full-canvas panes (fades, backdrops: size × global matrix at least 98 % of 1920x1080) keep the whole picture: nn::ui2d's draw constant-buffer setup (`nro0+0x75968`) and text setup (`nro0+0x8a1e0`) are the same SDK code as Mario Kart World 1.8.0's (the projection getter `nro0+0x66718` is the same five words; prologue, registers and the pane arguments match), so kinds 3 (`nro0+0x75a98`) and 4 (`nro0+0x8a2ec`) point x0 at a thread-local draw info holding the unscaled matrix, as [Mario Kart World](https://git.eden-emu.dev/moceure/BananaNative/src/tag/eden/v0.3.42/dm/games/0400C3F00006E000/README.md#aspect-ratio-android-180)'s `mkw_wide.c` does. Only a matrix kind 2 scaled counts, so the capture path `nro0+0xaf6440` (a pane drawn into a texture with its own ortho; the draw info's matrix saved and put back) and the per-player matrix `nro0+0x11da7e4` copies are left. `DM_MTF_HUD=0` leaves the layouts stretched with the frame (for comparing on the phone).
- **Open.** See [Open](#open): the world-anchored markers, doubles, which layouts the setup serves (unchecked), other readers of the camera's fovy.

## Swap2-Native

Current, 2026-11-18 (POCO F7 Ultra, Adreno 830):
